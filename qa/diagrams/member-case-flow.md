# Flow สมาชิกและเคสซ่อม (MVP local)

```mermaid
flowchart TD
    A[เว็บร้านหน้าเดียว] --> B[สมัครสมาชิก / เข้าสู่ระบบ]
    B --> C[FastAPI ตรวจบัญชีและสร้าง session cookie]
    C --> D{สิทธิ์บัญชี}
    D -->|User| E[แชท / ประวัติของตัวเอง / ส่งเคส]
    D -->|Admin| F[Dashboard นับเคส / ดูเคส / อัปเดตสถานะ]
    E --> G[ตรวจ user_id และ conversation ownership]
    G --> H[SQLite ใน Docker volume]
    E --> I[Redis cache → Vision → LightRAG → OpenAI]
    I --> J[บันทึกข้อความแชทตามเจ้าของบัญชี]
    J --> H
    E --> K[สร้างเลขเคส PLM-xxxxx และแนบบทสนทนาที่เลือก]
    K --> H
    F --> L[ตรวจ role=admin และขั้นตอนเปลี่ยนสถานะ]
    L --> M[เก็บสถานะ ราคาเสนอ หมายเหตุ เวลา และผู้แก้ไข]
    M --> H
    H --> N[สมาชิกดูสถานะและ timeline ของเคสตัวเอง]
    E --> O[ถามสถานะผ่านแชท]
    O --> G
    G --> P[อ่านสถานะเคสสดจาก SQLite ไม่ใช้ answer cache]
    P --> J
    M --> Q[ใบเสนอราคาแต่ละฉบับ]
    Q --> R[สมาชิกอนุมัติ / ปฏิเสธผ่านพอร์ทัล]
    R --> S[ตรวจเจ้าของและฉบับปัจจุบันใน transaction]
    S --> H
    S --> T[อนุมัติ: รอร้านเริ่มซ่อม / ปฏิเสธ: กลับตรวจเช็ค]
```

ลำดับสถานะ: ส่งเคส → ร้านรับเรื่อง → ตรวจเช็ค → รออนุมัติราคา → กำลังซ่อม → พร้อมรับเครื่อง → ปิดเคส (ยกเลิกได้ก่อนซ่อม)

สมาชิกกดยืนยันอนุมัติหรือปฏิเสธราคาในพอร์ทัลได้ ราคาใหม่ต้องอนุมัติใหม่ ระบบกันการข้ามอนุมัติก่อนเริ่มซ่อมงานที่มีราคาเสนอ ยังไม่มีระบบชำระเงินของลูกค้า ไฟล์ภาพใช้วิเคราะห์ครั้งนั้นและไม่เก็บเป็นประวัติภาพถาวร ข้อความแชทเก็บถาวรและเปิดย้อนหลังได้

RAG มีเฉพาะข้อมูลร้านและราคาสาธิต ไม่ ingest ประวัติส่วนตัวหรือเคสของสมาชิก

ระบบบน chatgpt.site เป็น static preview ส่วนสมาชิก SQLite เคส และ RAG ทำงานผ่าน Docker local
