# Plimo — แชทบอทผู้ช่วยร้านซ่อม iPhone (เนื้อหาสำหรับนำเสนอ)

เว็บจริง: https://203-156-66-86.sslip.io · ผลทดสอบทั้งหมด: [results/SUMMARY.md](results/SUMMARY.md)

## 1. โจทย์และแนวคิด

ร้านซ่อม iPhone ตอบคำถามซ้ำ ๆ ทั้งวัน (ราคา เวลาเปิด อาการเสีย) และต้องติดตามงานซ่อมหลายเคสพร้อมกัน
Plimo ใช้ **LLM เป็นแกนกลาง** ทำ 2 หน้าที่:

1. **ตอบลูกค้า** — ราคา ข้อมูลร้าน อาการ ดูรูป เปิดเคส ติดตามเคส อนุมัติราคา ชำระเงิน
2. **ช่วยแอดมิน** — สรุปเคส แนะนำสถานะถัดไป เสนอราคาจากแค็ตตาล็อก ร่างข้อความถึงลูกค้า สรุปคำถามประจำวัน

หลักการออกแบบ: **AI เสนอ คนหรือระบบยืนยัน** ตัวเลขราคา สถานะเคส และการชำระเงินมาจากฐานข้อมูลเสมอ ไม่ได้มาจากโมเดล

## 2. Feature list

### ลูกค้าทั่วไป (ไม่ต้องสมัคร)
- ถามข้อมูลร้าน ราคา อาการเสีย เป็นภาษาไทยธรรมดา ถามต่อเนื่องได้ ("แล้ว 14 ล่ะ")
- ส่งรูปหน้าจอ / ตัวเครื่อง / ข้อความแจ้งเตือนได้สูงสุด 3 รูป (รองรับรูปจาก iPhone)
- คำถามกำกวมจะถูกถามกลับ คำถามหลายเรื่องในข้อความเดียวตอบครบ

### สมาชิก
- เปิดเคสซ่อมจากแชท: ผู้ช่วยถามรุ่น/อาการที่ขาด สรุปให้ตรวจ แล้วสร้างเคสเมื่อกด "ยืนยัน" เท่านั้น
- ติดตามเคสด้วยเลข PLM ทุกรูปแบบ (PLM-00012, plm12, เคส 12, เลขไทย)
- อนุมัติ/ปฏิเสธใบเสนอราคาในแชทหรือในบัญชี
- ชำระเงินผ่าน Stripe Checkout (โหมดทดสอบ) และดูสถานะการชำระ
- ประวัติแชท รูปที่ส่ง และไทม์ไลน์ของเคส

### แอดมิน
- รายการเคสตามสถานะ เปลี่ยนสถานะตามลำดับที่อนุญาตเท่านั้น ส่งใบเสนอราคา
- **AI ช่วยแอดมิน**: สรุปเคส ข้อมูลที่ยังขาด สถานะที่ควรทำต่อ ราคาที่ควรเสนอ (ตรวจกับแค็ตตาล็อก) ร่างข้อความถึงลูกค้า
- เห็นรูปและบทสนทนาที่ลูกค้าแนบกับเคส (เช่นสลิป)
- Insight ประจำวัน: คำถามยอดนิยม คำถามที่ผู้ช่วยตอบไม่ได้ (ร้านควรเพิ่มข้อมูลอะไร)
- Metrics: จำนวนคำถาม cache hit ค่าใช้จ่าย AI ต่อวัน

## 3. Stack

| ชั้น | เทคโนโลยี | ทำไมเลือก |
|---|---|---|
| หน้าเว็บ | HTML/CSS/JS ล้วน (ไม่มี framework) | เบา โหลดเร็ว ไม่มี supply chain ฝั่ง frontend |
| Web server | nginx 1.31 + Caddy 2.10 (HTTPS อัตโนมัติ) | rate limit, security headers, cache ไฟล์; Caddy ออกใบรับรอง Let's Encrypt เอง |
| Backend | Python 3.12 · FastAPI · Uvicorn | async เรียก OpenAI/LightRAG พร้อมกันได้ |
| LLM | OpenAI `gpt-5.4-mini` (Responses API + JSON schema) | ถูกและเร็วพอสำหรับภาษาไทย; บังคับ output เป็นโครงสร้างได้ |
| RAG | LightRAG (โหมด `naive` vector search) + `text-embedding-3-small` | วัดแล้วแม่นและเร็วกว่าโหมด graph สำหรับคลังขนาดนี้ |
| Cache / rate limit | Redis 7.4 (เก็บลงดิสก์) | cache หลายชั้น, lock กันเรียกซ้ำ, ตัวนับต่อ IP/สมาชิก |
| ฐานข้อมูล | SQLite (WAL) | สมาชิก เคส ใบเสนอ การชำระ ประวัติแชท — พอสำหรับร้านเดียว สำรองง่าย |
| เก็บรูป | Cloudflare R2 (private) | รูปสลิป/ตัวเครื่องของสมาชิก ไม่มีลิงก์สาธารณะ |
| ชำระเงิน | Stripe Checkout (test mode) + webhook | ร้านไม่แตะเลขบัตรเลย |
| Deploy | Docker Compose บน VPS Ubuntu · `deploy.sh` คำสั่งเดียว | ติดตั้งซ้ำได้ ทุก image pin เวอร์ชัน |

## 4. เทคนิคหลัก

1. **Router แบบ structured output** — ทุกข้อความผ่าน LLM ตัวเล็กที่ตอบเป็น JSON: intent 9 แบบ, รุ่น, บริการ, เลขเคส, และ "คำถามฉบับเต็ม" ที่เขียนใหม่ให้เข้าใจได้โดยไม่ต้องอ่านบทสนทนา (แก้ "แล้ว 14 ล่ะ" ให้เป็น "เปลี่ยนหน้าจอ iPhone 14 ราคาเท่าไหร่")
2. **แยกเส้นทางตามงาน** — เคส/การชำระ ตอบจาก SQLite ตรง ๆ (ไม่ผ่าน LLM); นอกขอบเขต/ไม่ปลอดภัย ตอบข้อความคงที่; คำถามร้าน/ราคา/อาการ จึงใช้ RAG + LLM
3. **ราคาจากแค็ตตาล็อกเท่านั้น** — ระบบจับคู่รุ่น+บริการกับ `catalog.json` ส่งเข้า prompt แล้ว **ตรวจคำตอบ**: ถ้ามีตัวเลขบาทที่แค็ตตาล็อกไม่รองรับ จะแทนด้วยคำตอบจากแค็ตตาล็อกตรง ๆ
4. **RAG ที่วัดผลได้** — แยกเอกสารตามหัวข้อ (53 ชิ้น) วัด hit@1/hit@3/MRR แยกจากคำตอบ แล้วจูนจาก hit@1 31% → 72–88% และ hit@3 → 98–100%
5. **Cache 6 ชั้น + single-flight** — fast, router, retrieval, answer, vision, moderation; คำถามเดียวกันพร้อมกันเรียกโมเดลครั้งเดียว; key ผูกกับเวอร์ชันคลัง/prompt/โมเดล/แค็ตตาล็อก จึงไม่ตอบข้อมูลเก่า; ไม่ cache ผลที่ผิดพลาด
6. **Prompt caching ของ OpenAI** — ข้อมูลร้านทั้งหมดอยู่ส่วนต้นของ prompt ที่ไม่เปลี่ยน ทำให้ input 67–79% คิดราคาถูก
7. **AI เสนอ ระบบยืนยัน (human-in-the-loop)** — การเปิดเคส/อนุมัติราคาจากแชทเป็น "ข้อเสนอ" เก็บไว้ 10 นาที ทำจริงเมื่อลูกค้าพิมพ์ "ยืนยัน" และตรวจสิทธิ์/สถานะซ้ำตอนทำ; คำแนะนำ AI ของแอดมินถูกตรวจกับสถานะที่เปลี่ยนได้และแค็ตตาล็อกก่อนแสดง
8. **วิเคราะห์รูปเป็นขั้น** — ตรวจรูปมืด/ว่าง/เล็ก (ไม่เรียกโมเดล) → OpenAI moderation → vision จัดประเภท (ตัวเครื่อง, สลิป, บัตร/บัตรประชาชน, ไม่เกี่ยว) → เก็บเฉพาะรูปที่ควรเก็บ
9. **คุมค่าใช้จ่าย** — งบรายวัน (USD), มิเตอร์ต่อคำขอ, rate limit ต่อ IP/session/สมาชิก, ตั้ง deploy ให้ไม่สร้างคลังซ้ำถ้าเอกสารไม่เปลี่ยน
10. **ทดสอบเป็นระบบ** — eval อัตโนมัติ 143 ข้อ, API 24 endpoint, สุ่มกติกา ต้องทำ/ห้ามทำ, security 51 ข้อ, วงจรเคสเต็ม, load test

## 5. การป้องกัน (Guardrails)

| ความเสี่ยง | วิธีกัน |
|---|---|
| **แต่งราคา / ราคาผิดรุ่น** | ราคามาจากแค็ตตาล็อก + validator ตรวจตัวเลขทุกคำตอบ; Pro/Pro Max ห้ามใช้ราคารุ่นปกติ |
| **แต่งข้อมูลร้าน** (ที่อยู่, รับประกัน, ระยะเวลาซ่อม) | ตอบ "ทางร้านขอยืนยันเพิ่มเติม" เมื่อคลังไม่มีข้อมูล; ทดสอบด้วยคำถามที่ตั้งใจถามสิ่งที่ไม่มี |
| **Prompt injection** | ตัวกรองข้อความก่อนเรียกโมเดล, router จัด `unsafe` แล้วตอบข้อความคงที่, ข้อความลูกค้า/ภาพ/เอกสารถือเป็นข้อมูลไม่ใช่คำสั่ง |
| **เผย prompt / key / ข้อมูลภายใน** | key อยู่ฝั่ง server เท่านั้น; output validator แทนคำตอบที่มีคำภายใน |
| **ข้อมูลลูกค้าคนอื่น** | ทุก query ผูก `user_id`; เคสคนอื่นตอบเหมือน "ไม่มี" (ไม่บอกว่ามีอยู่) |
| **AI ทำรายการเกินสิทธิ์** | โมเดลไม่มี tool ทำรายการเอง; ทุก action ต้องยืนยันและตรวจซ้ำ |
| **จ่ายเงินปลอม / ยืนยันการชำระผิด** | ยอดเงินจาก DB, ยืนยันกับ Stripe API, webhook ตรวจลายเซ็น HMAC + เวลา + กันซ้ำ; แชทไม่รับเลขบัตรและไม่ยืนยันจากสลิป |
| **ข้อมูลส่วนตัว (PDPA)** | ซ่อนเลขบัตร (Luhn) และเลขบัตรประชาชน (checksum) ก่อนเก็บ/ส่ง; รูปบัตรไม่ถูกเก็บและไม่ทวนตัวเลข; ลบ EXIF/GPS จากรูป; log สถิติแบบไม่ระบุตัวตน |
| **รูปไม่เหมาะสม / ไม่เกี่ยว / อ่านไม่ออก** | moderation, จัดประเภท, ขอให้ถ่ายใหม่ — ไม่ตอบเรื่องรูปที่ไม่เกี่ยว |
| **คำถามนอกเรื่อง** (เขียนโค้ด, การบ้าน) | router `out_of_scope` ตอบข้อความคงที่ ไม่เสียค่าโมเดล |
| **ฟันธงอาการ** | prompt + เกณฑ์ทดสอบ: บอกสาเหตุที่เป็นไปได้และแนะนำตรวจเช็คฟรี |
| **ใช้งานเกิน / ค่าใช้จ่ายบาน** | rate limit 2 ชั้น (nginx + API), งบรายวัน, จำกัดขนาดข้อความ/รูป |
| **เว็บทั่วไป (OWASP Top 10:2025)** | CSP เข้ม, HSTS, cookie HttpOnly/Secure/SameSite, PBKDF2 600k, SQL parameter ทุกจุด, `textContent` ทุกจุด, จำกัดการ login, container ไม่รันเป็น root, pin ทุก dependency |
| **ระบบภายนอกล่ม** | router ล่ม → ใช้กฎ (เคสยังตอบได้); OpenAI/LightRAG ล่ม → ข้อความ error ปลอดภัย ไม่สร้างคำตอบปลอม; ผลที่ล้มไม่ถูก cache |

จับคู่กับ OWASP Top 10 for LLM 2026 และ OWASP Top 10:2025 ครบทุกหมวด: [guardrails.md](guardrails.md)

## 7. ข้อจำกัดที่บอกตรง ๆ

- ข้อมูลร้านบางอย่างยังไม่ยืนยัน (ที่อยู่, รับประกัน, ระยะเวลาซ่อม) บอทจึงตอบว่ายังไม่มีข้อมูล
- Stripe เป็นโหมดทดสอบ ไม่มีการคืนเงิน; ยังไม่มีรีเซ็ตรหัสผ่าน แจ้งเตือน และจองคิว
- LLM มีความแปรปรวน: ชุดทดสอบผ่านเกือบทั้งหมด แต่บางกรณีหลายเทิร์นยังพลาดได้ (ระบุในผลทดสอบ)
