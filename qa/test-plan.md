# แผนการทดสอบ Plimo iPhone Repair

แผนนี้อธิบายว่าทดสอบอะไร ทดสอบอย่างไร เกณฑ์ผ่านคืออะไร และผลล่าสุดอยู่ที่ไหน ทุกชุดรันซ้ำได้ด้วยคำสั่งเดียว ผลบนเซิร์ฟเวอร์จริงสรุปไว้ที่ [results/SUMMARY.md](results/SUMMARY.md) และในเอกสารส่งมอบ 2 ([docs/submission](../docs/submission/))

## 1. วัตถุประสงค์

1. ยืนยันว่าผู้ช่วยตอบ **ถูกต้องและตรงประเด็น** จากข้อมูลร้านจริง ไม่แต่งราคา นโยบาย หรือข้อมูลที่ร้านยังไม่ยืนยัน
2. ยืนยันว่า **ทุก endpoint** ในแผนภาพสถาปัตยกรรมทำงาน และตรวจสิทธิ์ถูกต้อง
3. ยืนยันว่า **RAG** ค้นเจอเอกสารที่ถูกต้อง และคำตอบภาษาไทยมาจากคลังความรู้
4. ยืนยันว่ากติกา **"ต้องทำ / ห้ามทำ"** ใน system prompt ถูกปฏิบัติจริง (สุ่มทดสอบ)
5. ยืนยันมาตรการ **ความปลอดภัย** ตาม OWASP Top 10:2025 และ OWASP Top 10 for LLM 2026
6. ยืนยันว่า **วงจรงานซ่อม** (เปิดเคส → เสนอราคา → อนุมัติ → ชำระเงิน → ปิดเคส) ทำงานครบด้วย AI จริง
7. วัด **ประสิทธิภาพและต้นทุน**: เวลาตอบ อัตรา cache hit และค่า AI ต่อคำตอบ

## 5. เกณฑ์ผ่าน

- แต่ละกรณีมีเกณฑ์อัตโนมัติ เช่น `must` (คำที่ต้องมี), `any` (มีอย่างน้อยหนึ่งคำ), `must_not` / `must_not_re` (คำ/รูปแบบที่ห้ามมี), `deny` (ห้ามยืนยันวลีนั้น แต่ยอมให้มีในประโยคปฏิเสธ), `num` / `not_num` (ตัวเลขราคาที่ต้องมี/ห้ามมี), `route` (เส้นทางของ router), `stored` (เก็บรูปหรือไม่), `verify_status` (สถานะเคสในฐานข้อมูลต้องไม่ถูกเปลี่ยน)
- ชุดผ่านเมื่อทุกกรณีผ่าน กรณีที่ไม่ผ่านต้องรายงานตามจริงในไฟล์ผล ห้ามซ่อน
- **การตรวจคะแนนซ้ำ** (`run_eval.py --regrade`) ใช้ได้เฉพาะเมื่อเกณฑ์แคบเกินไปแต่คำตอบถูกต้องตามความหมาย ต้องตรวจจากคำตอบเดิม (ไม่ถามใหม่) และบันทึกในรายงานทุกครั้ง รอบส่งงานมี 1 กรณี (K17: ตอบ "ยืนยันไม่ได้" ซึ่งความหมายเดียวกับเกณฑ์)
- ตัวเลขเวลาตอบเป็นเวลาจริงผ่านอินเทอร์เน็ต วัดจากเครื่องผู้ทดสอบ

## 7. ลำดับการรันก่อนส่งงาน

1. `docker compose exec -T api python -m unittest …` (ไม่เสียค่า API)
2. deploy ด้วย `bash deploy/deploy.sh ubuntu@<server>` (คลังความรู้ซิงก์อัตโนมัติ)
3. T5 → T2 → T3 → T4 → T6 → T7 บน VPS (T7 รันหลัง T6 ได้เพราะสคริปต์รอโควตาเอง)
4. `python3 qa/build_summary.py` สร้าง [results/SUMMARY.md](results/SUMMARY.md) จากผลจริง
